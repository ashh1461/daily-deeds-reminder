# Wird — APK Static Security Audit

**Date:** 2026-11-27
**Scope:** Authorized, local, read-only static security assessment of the owner's **own** release APK. No live server, network, or account was touched.
**Analyst tooling:** Android SDK build-tools 36.0.0 (`apksigner`, `aapt2`), isolated APK extraction + DEX string scan, and cross-reference against the app's own source tree for precise line references.

## Executive summary

Wird is a **local-only, offline-first** prayer-times / adhan / Quran–Mafatih reader. The audit **confirms the prior assumption**: the app stores no credentials and talks to no backend. Its only network use is a single HTTPS channel to GitHub to fetch optional adhan voice packs, and that path is unusually well hardened (host allow-list, SHA-256 verification, size caps). The attack surface is therefore almost entirely **local** — exported components, backup, and direct-boot storage — and all of it is in good shape.

**No CRITICAL or HIGH findings.** The items below are LOW / INFO defense-in-depth and privacy observations. Several areas were reviewed and found genuinely solid; they are listed under "Confirmed good" so they are not re-flagged later.

## Findings

### F-1 — Whole settings file placed in device-protected (direct-boot) storage — **LOW** (privacy / data-minimization)

- **Where:** `app/src/main/java/com/dailydeeds/reminder/data/PrefsStorage.kt:50` (`open()` → `createDeviceProtectedStorageContext()`, `moveSharedPreferencesFrom`), consumed by `app/src/main/java/com/dailydeeds/reminder/data/PreferencesManager.kt:26`.
- **What:** Since 1.8.2 the **entire** `daily_deeds_prefs` SharedPreferences file is moved into device-protected storage so prayer alarms can be rescheduled before the first unlock after a reboot. That file includes data that is **not** needed before unlock: the user's saved location (`pref_place_lat` / `pref_place_lng` / `pref_place_name`, `PreferencesManager.kt:279`) and the Khums financial draft / year (`worship_khums_draft`, `worship_khums_year`, `PreferencesManager.kt:333`,`:327`).
- **Impact:** Device-protected storage remains app-private and file-based-encrypted, but with the **device** key rather than the user credential — i.e. it is decryptable before the first unlock after a reboot. On a lost/stolen or rooted device subjected to forensic extraction in the pre-unlock window, location and the Khums financial figures would be readable, whereas credential-protected storage would not yet be. This is a confidentiality *delta*, not an exploitable vulnerability; other apps cannot read it without root.
- **Fix (optional, defense-in-depth):** Keep only the keys the boot receiver actually needs before unlock in device-protected storage (prayer settings, alarm configs `pref_alarm_cfg_*`, reminder times, and the location used for prayer-time calculation if boot-time scheduling needs it). Hold the remaining non-alarm data (Khums draft/year, favorites, reading positions, deed history) in credential-protected storage. The existing `DirectBoot.bootWork()` split already models "prayer-only vs all", so a two-store split is a natural extension. If the simpler single-store design is preferred, document the tradeoff and confirm location is genuinely required at boot.
- **Status — Addressed (2026-11-27, branch `fix/security-hardening`).** The settings file was split into two SharedPreferences stores. The device-protected `daily_deeds_prefs` now holds **only** the keys the locked boot/alarm path reads before unlock — verified against `ReligiousAlarms.schedulePrayer`/`restoreSnoozes`, `PrayerAlarmReceiver`, `AdhanService` and `AdhanActionReceiver`: prayer settings, `pref_alarm_cfg_*` (+ legacy `pref_prayer_alarm_*`), hijri offset, adhan-global, the Imsak flag, `alarm_last_handled`, `alarm_pending_snoozes`, and the place (`pref_place_*`). The place **is** required before unlock (the pre-unlock path recomputes prayer times via `AdhanPlanner`, which needs latitude/longitude/time-zone); this is documented in `PrefsClassifier.kt` and `docs/PRIVACY.md`. Everything else — **the Khums draft/year**, favorites, reading positions, deed history, theme and reminder times — moved to the new credential-protected `daily_deeds_user_prefs`. A one-time split runs on the first unlocked launch and cleanly migrates both the 1.8.2–1.8.4 layout (whole file in device storage) and a direct upgrade from pre-1.8.2 (whole file still in credential storage); nothing is lost and the credential store is never opened before unlock. Backup/restore round-trips every key regardless of its store (`PreferencesManager.exportForBackup`/`importFromBackup`, `BackupCodec` unchanged). Covered by `PrefsClassifierTest`, `DirectBootTest` and the instrumented `PrefsStorageInstrumentedTest`.

### F-2 — Voice-pack integrity hash is served from the same origin as the file; no certificate pinning — **LOW** (supply-chain)

- **Where:** `app/src/main/java/com/dailydeeds/reminder/adhan/VoiceModels.kt:24` (`MANIFEST_URL` points at the mutable `master` branch), `:52` (`VoiceManifest.parse`), and `app/src/main/java/com/dailydeeds/reminder/adhan/VoicePackDownloader.kt:50` (SHA-256 check against the manifest-supplied hash).
- **What:** The downloader verifies each voice file against a SHA-256 that is itself listed in `manifest.json`, which is fetched from the **same** GitHub origin as the audio. The hash therefore protects against corruption and TLS-less tampering, but **not** against a compromise of the GitHub account/repo (or a mis-published manifest), because an attacker who controls the origin controls both the file and its expected hash. There is no certificate/public-key pinning on this channel, so trust rests on the system CA store + GitHub's TLS and account security.
- **Impact:** Limited. A compromised origin could deliver an attacker-chosen `.ogg`, which is then decoded by the platform media stack (`MediaMetadataRetriever` / the adhan `MediaPlayer`). Worst realistic case is a media-codec exploit attempt against a device that chose to download a pack; there is no privilege escalation path in-app (the file is written to app-private storage under a regex-validated id). Severity is held at LOW because it requires GitHub-side compromise and user opt-in to download.
- **Fix (optional):** For a hobby/personal distribution this is acceptable as-is. To raise the bar: pin the GitHub leaf/intermediate (or ship a signed manifest — detached signature over `manifest.json` verified with a public key baked into the APK), and/or pin voice-pack hashes in the shipped build rather than trusting the live manifest. At minimum, keep the `master`-branch dependency in mind: a tagged/immutable path would reduce the "someone force-pushed a bad manifest" window.
- **Status — Addressed (2026-11-27, branch `fix/security-hardening`).** Two cheap, key-free measures close the "force-pushed / mis-published manifest" scenario: (1) `VoiceUrlPolicy.MANIFEST_URL` now points at an **immutable commit SHA** (`VoiceUrlPolicy.MANIFEST_COMMIT`) instead of `master`, so GitHub serves the manifest by content-addressed commit and a branch force-push cannot change what a released build fetches; and (2) the downloader verifies the fetched manifest bytes against a **SHA-256 pinned in the build** (`VoiceManifest.EXPECTED_SHA256`) before parsing, so a manifest swapped at the origin is rejected even though the file and its per-voice hashes share one origin. Because the APK is owner-signed, that baked-in digest is as trustworthy as a public key, with no separate signing key to manage. All existing protections are unchanged: HTTPS + host allow-list re-checked after every redirect, no userinfo, port pinned to 443, ≤3 redirects, declared/streamed size caps, and the per-voice SHA-256 verified before a part file is committed. When the owner updates the manifest: push it, then bump `MANIFEST_COMMIT` and `EXPECTED_SHA256` and release — a unit test (`theRepoManifestMatchesThePinnedDigest`) fails the build if the two drift. Covered by three new tests in `VoiceAndPolicyTest`.

### F-3 — `MainActivity` is exported and accepts intent extras from any app — **INFO** (by design; no data exposure)

- **Where:** `AndroidManifest.xml` line 44–57 (`exported=true`, LAUNCHER filter); handling in `app/src/main/java/com/dailydeeds/reminder/MainActivity.kt:133`,`:178`,`:191`.
- **What:** Because it is the launcher activity it is necessarily exported, so a co-located app can `startActivity` it with extras. The handlers read only: `EXTRA_STOP_ADHAN` (boolean → stops a playing adhan), `EXTRA_OPEN_TODAY` (boolean → navigate to Today), and `EXTRA_CATEGORY` (string, but matched against the fixed `DeedCategory` enum names at `MainActivity.kt:192` — unknown values are ignored).
- **Impact:** Negligible. The worst a third-party app can do is launch Wird to the foreground and silence a currently-playing adhan, or preselect a deed-category tab — benign UI actions. No untrusted value reaches a file path, SQL, `WebView`, reflection, or dynamic component dispatch. There is **no** `VIEW`/deep-link intent filter, so there is no URL-driven surface. No change required; recorded so the exported activity is not mistaken for an open sink in future reviews.

### F-4 — `androidx.profileinstaller.ProfileInstallReceiver` exported — **INFO** (library component, permission-protected)

- **Where:** `AndroidManifest.xml` lines 126–131.
- **What:** This is the standard AndroidX ProfileInstaller receiver, `exported=true` but guarded by `android:permission="android.permission.DUMP"`, a signature/privileged permission held only by the system and `adb shell`.
- **Impact:** None for ordinary apps; only shell/system can trigger it. Expected in any Compose/Jetpack app. No action.

## Confirmed good (reviewed, no issue)

- **Signing — verified.** APK Signature Scheme **v2 = true, v3 = true** (v1 JAR not needed at minSdk 26; v3.1/v4 absent, fine). Single signer, `CN=Wird, O=ashh1461`, **RSA 4096**. Certificate SHA-256 `9b0c292bcc9e1f973032fcb2dfb4aa9e79a4164986038856c1092a9b5cf1ff36` — **matches the expected release cert** (`9b0c292b…f1ff36`).
- **Manifest flags.** `allowBackup=false`, `dataExtractionRules` set, `networkSecurityConfig` set, `extractNativeLibs=false`. **No `android:debuggable`** (release build is not debuggable). No `usesCleartextTraffic="true"`.
- **Permissions** are all justified for the feature set: `POST_NOTIFICATIONS`, `SCHEDULE_EXACT_ALARM`, `RECEIVE_BOOT_COMPLETED`, `VIBRATE`, `ACCESS_COARSE_LOCATION` (prayer-time/Qibla calc), `FOREGROUND_SERVICE(+_MEDIA_PLAYBACK)` (adhan playback), `WAKE_LOCK`, `INTERNET` (voice-pack download only). No dangerous/over-broad permissions (no `READ/WRITE_EXTERNAL_STORAGE`, no `ACCESS_FINE_LOCATION`, no SMS/contacts/camera/mic).
- **Exported components.** Every app-authored service and receiver is `exported=false` (`AdhanService`, `DailyReminderReceiver`, `PrayerAlarmReceiver`, `AdhanActionReceiver`, `OccasionAlarmReceiver`, `BlessedEveReceiver`, `BootReceiver`, `PrayerWidgetProvider`). `BootReceiver` listens for protected system broadcasts only. `InitializationProvider` is `exported=false`. Dynamically-registered receivers are protected by the auto-generated signature permission `…DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`.
- **Network security config** (`res/xml/network_security_config.xml`): `cleartextTrafficPermitted="false"` base-config — no cleartext anywhere.
- **No secrets / no backend.** DEX + resource/asset string scan found **no** API keys, tokens, JWTs, private keys, Firebase config, or `google-services.json`. The only URLs present are the GitHub voice manifest (HTTPS), CreativeCommons attribution links, and library/schema URLs. No `http://` endpoints. `assets/` contains only adhan `.ogg` audio and dexopt baseline profiles; no bundled certificates. Native libs are only `libandroidx.graphics.path.so` (standard AndroidX).
- **Backup codec is hardened** (`app/src/main/java/com/dailydeeds/reminder/data/BackupCodec.kt`): a backup file is treated as untrusted input — allow-listed keys only (`:22`), per-key type validation (`:108`), 2 MB / 20,000-entry / 100 KB-string caps (`:18`–`:20`), and whole-record place validation (`:121`) so a malformed location can't crash prayer calculation. Combined with `allowBackup=false`, `adb backup` yields nothing and a hand-crafted restore file cannot inject arbitrary preferences.
- **Voice download path is hardened** (`VoicePackDownloader.kt`, `VoiceModels.kt`, `VoiceStore.kt`): HTTPS + host allow-list **re-checked after every redirect** (`VoicePackDownloader.kt:59`) with no userinfo and port pinned to 443 (`VoiceModels.kt:35`) — SSRF-resistant; manual redirect handling capped at 3 (`:58`,`:100`); declared-length and streamed size caps (`:32`,`:41`); SHA-256 verified before the part file is committed, with cleanup on any failure (`:51`–`:53`). File names derive from a regex-validated id `[a-z0-9_]{1,40}` (`VoiceModels.kt:47`), and `importOwn` generates its own id rather than using the user's filename (`VoiceStore.kt:59`) — **no path traversal**. Imported audio is MIME-checked, size-capped, and must decode (`VoiceStore.kt:52`–`:84`).

**Bottom line:** No credential storage and no backend were confirmed, signing is correct and strong, the manifest is tight, and the two surfaces that *could* have been dangerous (backup restore and voice-pack download) are both carefully validated. The only substantive items are two optional LOW defense-in-depth hardening ideas. This is a clean result for a local-first app.
